# Стратегия вывода Apache Camel / legacy ESB

## Почему это нужно отдельно описать

В текущей архитектуре Apache Camel выполняет не только роль транспорта между системами. В ESB могут быть сосредоточены:

- маршрутизация между системами;
- форматно-логический контроль;
- пакетные и потоковые трансформации;
- retry, dead letter queue, идемпотентность и другие паттерны надёжности;
- оркестрация процессов;
- часть бизнес-логики.

Поэтому целевая архитектура не рассматривает API Gateway и Event Bus как полную замену ESB. API Gateway и Event Bus закрывают только транспорт: синхронные API и асинхронные события.

Остальная ответственность Apache Camel должна быть разнесена по целевым архитектурным слоям.

## Декомпозиция ответственности ESB

| Ответственность Apache Camel в As-Is | Целевой компонент в To-Be |
| --- | --- |
| Синхронный транспорт | API Gateway + доменные API |
| Асинхронный транспорт | Event Bus |
| Маршрутизация между системами | Integration Layer / Event Routing |
| Форматно-логический контроль | Domain Validators / Data Contracts / Policy Checks |
| Трансформации сообщений | Anti-Corruption Layer / Mapping Services |
| Пакетные трансформации | Data Platform Ingestion Pipelines |
| Retry / DLQ | Event Bus reliability patterns |
| Идемпотентность | Consumer Services / Idempotency Keys |
| Оркестрация процессов | Domain Services или Process Manager внутри конкретного домена |
| Бизнес-логика | Domain Services |
| Legacy routes | Legacy Adapter / Strangler Layer |

## Этапы вывода ESB

### 1. Инвентаризация маршрутов

Для каждого Camel route фиксируются:

- источник и получатель;
- тип интеграции: sync / async / batch / stream;
- наличие ФЛК;
- наличие трансформаций;
- наличие retry / DLQ / идемпотентности;
- наличие бизнес-логики;
- критичность для бизнеса;
- владелец маршрута.

### 2. Классификация ответственности

Каждый route разбивается на набор ответственностей:

- transport;
- validation;
- transformation;
- reliability;
- orchestration;
- business logic;
- legacy compatibility.

Это нужно, чтобы не перенести скрытую бизнес-логику из ESB в новый транспортный слой.

### 3. Перенос транспорта

Простые синхронные маршруты переносятся в API Gateway и доменные API.  
Асинхронные маршруты переносятся в Event Bus.

### 4. Перенос ФЛК и проверок

Форматно-логический контроль переносится:

- в domain validators;
- в data contracts;
- в policy checks;
- в data quality checks для аналитических потоков.

### 5. Перенос трансформаций

Трансформации переносятся:

- в Anti-Corruption Layer для legacy-интеграций;
- в Mapping Services для доменных API;
- в ingestion pipelines для аналитической платформы.

### 6. Перенос бизнес-логики

Если в Camel route есть бизнес-решения, они переносятся в соответствующий доменный сервис.

Пример:

- финансовые правила → Fintech Domain;
- медицинские процессы → Clinical Domain;
- правила партнёрской интеграции → Partner Domain;
- корпоративные правила → Corporate Domain.

### 7. Временный режим

До полного вывода Apache Camel остаётся как legacy integration adapter.  
Новая бизнес-логика, новые проверки и новые трансформации в Camel не добавляются.

### 8. Вывод из эксплуатации

После переноса маршрутов:

- отключаются перенесённые routes;
- проверяется отсутствие потребителей;
- обновляется документация в Data Catalog / Integration Catalog;
- ESB выводится из критического контура.
