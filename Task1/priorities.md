# Приоритизация проблем

Метод приоритизации: MoSCoW.

Критерии:

- влияние на выручку;
- влияние на time-to-market;
- влияние на качество медицинских и финансовых сервисов;
- влияние на безопасность данных;
- влияние на масштабируемость.

## Must have

Эти проблемы нужно решать в первую очередь. Без них целевое состояние не заработает.

| Проблема | Почему Must | Бизнес-цель |
|---|---|---|
| Перегруженный legacy DWH | DWH стал главным узким местом для отчётности и изменений | скорость отчётности, time-to-market |
| Бизнес-логика внутри DWH | Новые направления требуют изменений в DWH | независимое развитие доменов |
| Нет доменных границ | Финтех, ИИ и медицина блокируют друг друга | масштабирование бизнеса |
| Нет self-service data portal | Бизнес зависит от IT для построения отчётов | быстрая аналитика |
| Нет semantic layer | Метрики считаются по-разному | единые KPI |
| Нет Data Catalog и Lineage | Нельзя доверять отчётам и быстро искать данные | качество данных и аудит |
| Медицинские данные смешаны с аналитикой | Риск использования запрещённых данных в отчётности | безопасность и регуляторика |
| Нет стандартного API/Event подхода | Новые партнёры подключаются дорого и долго | подключение новых бизнесов |

## Should have

Нужно внедрить сразу после базовой декомпозиции.

| Проблема | Почему Should | Бизнес-цель |
|---|---|---|
| Старый ESB перегружен | Интеграции хрупкие, но можно мигрировать поэтапно | устойчивость интеграций |
| PowerBuilder зависит от DWH | Операторские процессы нельзя развивать независимо | развитие клиник |
| Power BI сильно кастомизирован | Можно сохранить временно, но нужно перевести на semantic layer | self-service аналитика |
| Нет облачного масштабирования аналитики | Сложные отчёты требуют гибких ресурсов | производительность |
| Нет data contracts | Данные между доменами передаются без понятных правил | качество интеграций |

## Could have

Полезно для развития, но не блокирует первый этап.

| Проблема | Почему Could | Бизнес-цель |
|---|---|---|
| Полная замена всех legacy-экранов | Можно оставить часть legacy через adapter | снижение рисков миграции |
| Полная миграция всех исторических данных сразу | Можно начать с критичных срезов и архивов | снижение стоимости |
| Реализация всех data products сразу | Можно начать с ключевых KPI и доменов | быстрый эффект |
| Полная автоматизация onboarding новых партнёров | Можно сначала стандартизировать API и события | развитие экосистемы |

## Won't have на первом этапе

Не нужно делать в первый год или до стабилизации базовой архитектуры.

| Инициатива | Почему не сейчас |
|---|---|
| Big bang миграция всего DWH | Высокий риск остановить отчётность и бизнес-процессы |
| Полный отказ от legacy DWH за один релиз | Нужен поэтапный strangler-подход |
| Перенос медицинских карт в self-service аналитику | Противоречит условию: медицинские карты и исследования не включаются в витрину |
| Единая универсальная модель данных для всех доменов | Лучше использовать доменные модели и data contracts |
| Сразу микросервисная декомпозиция всех процессов | Риск получить распределённый монолит |

## Приоритетный roadmap проблем

### P0 — немедленно

1. Отделить медицинские карты и исследования от аналитической витрины.
2. Зафиксировать домены: Medical, Fintech, AI, Corporate, Partner.
3. Ввести Data Catalog, ownership и data contracts.
4. Спроектировать self-service data portal и semantic layer.
5. Начать вынос бизнес-логики из DWH.

### P1 — первый этап миграции

1. Создать lakehouse / cloud data platform.
2. Настроить ingestion из legacy DWH и доменных систем.
3. Создать первые curated marts для управленческой отчётности.
4. Перевести BI на semantic layer.
5. Подключить Event Bus и API Gateway для новых интеграций.

### P2 — развитие

1. Мигрировать PowerBuilder-функции в новые UI/API.
2. Перевести домены на собственные хранилища.
3. Сократить роль SQL Server 2008 до read-only архива.
4. Подключить фармацевтические компании и производителя электроники через стандартные контракты.
5. Расширить self-service до конструктора отчётов.
