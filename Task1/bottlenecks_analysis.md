# Анализ проблемных мест As-Is

## Краткий вывод

Главное узкое место As-Is архитектуры — перегруженный DWH на SQL Server 2008.

Сейчас DWH одновременно выполняет роли:

- хранилища данных;
- источника отчётности;
- места бизнес-логики;
- интеграционного центра;
- источника данных для BI, операторов, финтеха и ИИ.

Из-за этого любое новое направление требует изменений в DWH, а сложные отчёты строятся часами.

## Проблемные места

| Проблема | Что происходит сейчас | Какой бизнес-сценарий страдает | Последствие |
|---|---|---|---|
| DWH стал центром всей бизнес-логики | В SQL Server 2008 хранится не только аналитика, но и значительная часть бизнес-правил | Быстрое подключение новых бизнесов | Любое изменение требует доработки DWH |
| Отчёты строятся часами | Большой объём данных и много трансформаций внутри DWH | Быстрая управленческая отчётность | Решения принимаются с задержкой |
| SQL Server 2008 устарел | Ограничения по масштабированию, поддержке и эксплуатации | Масштабирование данных и аналитики | Рост стоимости поддержки и рисков отказа |
| PowerBuilder зависит от DWH | Операторский интерфейс связан с legacy-логикой | Развитие клиник и операторских процессов | Нельзя независимо развивать клинические процессы |
| BI сильно кастомизирован поверх DWH | Power BI использует тяжёлые запросы и кастомные модели | Self-service аналитика | Пользователи зависят от IT-команды |
| Нет доменных границ | Медицинские, финтех-, ИИ- и корпоративные данные смешаны | Независимое развитие направлений | Команды блокируют друг друга |
| Старый ESB на Apache Camel перегружен интеграциями | ESB используется как общий транспорт между разными направлениями | Подключение фармы, электроники и новых партнёров | Интеграции становятся хрупкими |
| Нет data products | Данные не оформлены как управляемые продукты с владельцами и контрактами | Масштабирование self-service аналитики | Каждая витрина собирается вручную |
| Нет единого каталога данных | Пользователи не понимают, какие данные доступны и кому они принадлежат | Конструирование собственных отчётов | Рост хаоса и дублирование витрин |
| Нет lineage | Не видно, из каких источников собран отчёт | Доверие к отчётности и аудит | Сложно найти причину ошибки в отчёте |
| Медицинские данные могут попадать в аналитику | DWH содержит медицинские карты, исследования и историю болезни | Безопасная аналитика | Риск нарушения требований по медицинским данным |
| Нет единого semantic layer | Метрики считаются по-разному в разных отчётах | Целостное представление KPI | Несогласованные бизнес-показатели |
| Нет изоляции доменов в инфраструктуре | Все направления завязаны на общий legacy-ландшафт | Независимое развитие финтеха и ИИ | Изменения одного домена влияют на другие |
| Нет гибкого облачного масштабирования | Большая часть ландшафта держится на legacy-инфраструктуре | Рост объёмов данных до сотен ТБ | Невозможно быстро выделить ресурсы под отчёты |
| Нет стандарта подключения новых направлений | Фарма и производитель электроники будут подключаться индивидуально | Быстрое подключение новых бизнесов | Высокий time-to-market |

## Ключевые бизнес-сценарии и влияние проблем

### 1. Быстрая подготовка отчётности

Страдает из-за:

- тяжёлых трансформаций в DWH;
- отсутствия готовых витрин;
- отсутствия semantic layer;
- отсутствия data products.

Целевое решение:

- lakehouse;
- curated data marts;
- query engine;
- semantic layer;
- self-service data portal.

### 2. Независимое развитие финтех-направления

Страдает из-за:

- смешения финтех-логики с общим DWH;
- отсутствия доменных границ;
- старого интеграционного слоя.

Целевое решение:

- Fintech Domain Services;
- отдельные финтех data products;
- API Gateway;
- Event Bus;
- собственные доменные хранилища.

### 3. Независимое развитие ИИ-направления

Страдает из-за:

- прямой зависимости от медицинских данных в DWH;
- отсутствия безопасных data contracts;
- отсутствия контроля состава данных.

Целевое решение:

- AI Domain Services;
- отдельный доступ к медицинским данным через policy checks;
- запрет попадания медицинских карт и исследований в аналитическую витрину;
- data contracts и аудит.

### 4. Подключение новых бизнесов

Страдает из-за:

- отсутствия стандартной схемы интеграции;
- хрупкой ESB-интеграции;
- отсутствия data products.

Целевое решение:

- API Gateway;
- Event Bus;
- Integration Services;
- data product onboarding;
- Data Catalog.

### 5. Целостное представление KPI

Страдает из-за:

- разрозненных расчётов в DWH и BI;
- отсутствия общего semantic layer;
- отсутствия владельцев метрик.

Целевое решение:

- Metrics Store / Semantic Layer;
- Data Governance;
- Data Catalog;
- утверждённые KPI-модели.
