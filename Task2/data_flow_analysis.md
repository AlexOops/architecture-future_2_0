# Анализ потоков данных

## Основной поток аналитики

```text
Domain Systems
-> Data Contracts
-> Ingestion
-> Lakehouse
-> Curated Data Marts
-> Semantic Layer
-> Self-service Data Portal / BI
```

Назначение:

- ускорить построение отчётов;
- убрать тяжёлые трансформации из legacy DWH;
- дать бизнесу конструктор отчётов;
- сохранить единые KPI.

## Поток 1. Быстрая подготовка отчётности

| Шаг | Поток | Что происходит |
|---|---|---|
| 1 | домены -> ingestion | домены публикуют data products по контрактам |
| 2 | ingestion -> lakehouse | данные загружаются в raw/trusted/curated зоны |
| 3 | lakehouse -> marts | формируются готовые витрины |
| 4 | marts -> semantic layer | метрики приводятся к единой бизнес-модели |
| 5 | portal/BI -> semantic layer | пользователь собирает отчёт без запроса к legacy DWH |

Бизнес-эффект:

- отчёты строятся быстрее;
- бизнес меньше зависит от IT;
- KPI считаются одинаково во всех доменах.

## Поток 2. Интеграция нового финтех-сервиса

```text
Fintech Service
-> Fintech DB
-> Event Bus
-> Data Product
-> Data Platform
-> Semantic Layer
-> BI / Portal
```

Что меняется:

- финтех-логика остаётся в Fintech Domain;
- DWH не дорабатывается под каждый новый банковский продукт;
- отчётность получает финтех-данные через data product.

Бизнес-эффект:

- быстрее запускать новые финансовые сервисы;
- проще соблюдать банковские требования;
- изменения финтеха меньше влияют на клиники и AI.

## Поток 3. Использование AI для медицинских данных

```text
Clinical Domain
-> Policy Check
-> AI Domain
-> AI Processing
-> AI Result
-> Clinical Domain
```

Ограничение:

- медицинские карты, истории болезней и результаты исследований не публикуются в self-service аналитику;
- AI получает только разрешённый набор медицинских данных;
- результат AI возвращается в клинический контур.

Бизнес-эффект:

- AI можно развивать независимо;
- медицинские данные остаются под контролем;
- результаты AI используются врачами и клиническими процессами.

## Поток 4. Подключение партнёра

```text
Partner System
-> API Gateway
-> Partner Domain
-> Event Bus
-> Partner Data Product
-> Data Platform
```

Примеры партнёров:

- фармацевтическая компания;
- производитель электроники;
- поставщик медицинского оборудования.

Что важно:

- каждый партнёр подключается по стандартному контракту;
- события и данные проходят через gateway;
- данные публикуются в каталог;
- не требуется менять legacy DWH.

Бизнес-эффект:

- быстрее подключать новые бизнес-направления;
- ниже стоимость интеграции;
- меньше точечных связей между системами.

## Поток 5. Постепенная миграция legacy DWH

```text
Legacy DWH
-> Legacy Adapter
-> Ingestion
-> Lakehouse
-> Data Marts
```

Назначение:

- не отключать legacy DWH сразу;
- сохранить исторические данные;
- постепенно переносить отчётность;
- снижать роль SQL Server 2008 до read-only источника.

Бизнес-эффект:

- меньше риск остановки отчётности;
- можно мигрировать доменами;
- legacy перестаёт быть центром новой логики.

## Контроль потоков

| Контроль | Где применяется | Зачем |
|---|---|---|
| Data Contract | между доменами и data platform | стабильные схемы и SLA |
| Data Catalog | для всех data products | поиск данных и владелец |
| Lineage | ingestion, marts, semantic layer | доверие к отчётам |
| Policy Check | medical и fintech данные | доступ по правилам |
| Masking | portal, BI, query layer | защита чувствительных данных |
| Audit Log | доступ к данным и отчётам | расследование инцидентов |
| Quality Checks | ingestion и marts | контроль качества данных |
