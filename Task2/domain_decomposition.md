# Обоснование разделения на домены

## Проблема As-Is

Сейчас DWH на SQL Server 2008 выполняет слишком много ролей:

- хранит корпоративные данные;
- содержит бизнес-логику;
- обслуживает BI;
- поддерживает операторский интерфейс PowerBuilder;
- является источником данных для финтех- и ИИ-сервисов;
- участвует в интеграциях через ESB.

Из-за этого новые бизнес-сценарии требуют доработки DWH. Это замедляет time-to-market и делает развитие направлений зависимым друг от друга.

## Целевой принцип

Каждый домен должен владеть своими процессами, данными и data products.

DWH и аналитическая платформа не должны быть местом реализации доменной бизнес-логики. Их задача — хранить подготовленные аналитические данные, витрины, метрики и исторические срезы.

## Домены

| Домен | Зона ответственности | Данные | Зачем выделять |
|---|---|---|---|
| Clinical Domain | клиники, пациенты, приёмы, операционные медицинские процессы | клинические события, пациенты, записи, статусы лечения | клиники развиваются независимо от финтеха и аналитики |
| Medical Records Boundary | медицинские карты, истории болезни, исследования | medical records, diagnostic results, images | эти данные не включаются в self-service витрину |
| Fintech Domain | банковские продукты, счета, кредиты, финансовая история | счета, кредиты, транзакции, финтех-профили | финтех можно развивать с банковскими требованиями и отдельным релизным циклом |
| AI Domain | ИИ-диагностика и медицинские AI-сценарии | задания AI, результаты анализа, модели, inference events | AI развивается отдельно, но с контролируемым доступом к медицинским данным |
| Partner Domain | фармацевтика, электроника, новые внешние бизнесы | partner contracts, product catalog, device telemetry, partner events | новых партнёров можно подключать через стандартные контракты |
| Corporate Domain | персонал, инвентаризация, управленческие финансы | HR, inventory, corporate finance | внутренние процессы отделены от клинических и финтех-сценариев |
| Data Platform Domain | аналитика, витрины, метрики, каталог, lineage | data products, curated marts, KPI, metadata | быстрая отчётность и self-service без прямой зависимости от DWH |
| Governance Domain | доступ, политики, качество, каталог, lineage | роли, policies, metadata, contracts | единые правила доступа, качества и публикации данных |

## Границы медицинских данных

Медицинские карты, истории болезни и результаты диагностических исследований не публикуются в self-service аналитическую витрину.

Разрешены только:

- агрегированные показатели;
- обезличенные или псевдонимизированные наборы;
- операционные события без содержимого медкарты;
- результаты, разрешённые политиками доступа.

AI Domain может использовать медицинские данные только через контролируемый доступ:

```text
Clinical Domain -> Policy Check -> AI Domain -> AI Result -> Clinical Domain
```

## Как домены обмениваются данными

| Способ | Где использовать | Пример |
|---|---|---|
| API | синхронные запросы и команды | создать заявку на AI-анализ |
| Event Bus | доменные события | payment_created, appointment_completed |
| Data Product | аналитические данные домена | fintech_transactions_mart |
| Data Contract | описание схемы и SLA данных | contract для партнёра или BI |
| Catalog + Lineage | поиск и контроль происхождения | владелец, источник, путь данных |

## Преимущества для бизнеса

### Ускорение вывода продуктов

Новый финтех-сервис больше не требует изменения общей DWH-логики. Он развивается внутри Fintech Domain и публикует нужные события и data products.

### Снижение зависимости от DWH

DWH перестаёт быть источником всей логики. Legacy DWH остаётся временным источником через adapter, а новые сценарии строятся через доменные сервисы и data platform.

### Независимое развитие направлений

Медицина, финтех, AI и партнёры могут иметь разные команды, релизные циклы, требования безопасности и модели данных.

### Масштабирование новых бизнесов

Фармацевтические компании и производитель электроники подключаются через Partner Domain, API Gateway, события и data contracts.

### Быстрая отчётность

Self-service portal работает с curated marts и semantic layer, а не с тяжёлыми SQL-трансформациями в SQL Server 2008.

## Что не делать

- Не строить новые сценарии напрямую поверх legacy DWH.
- Не добавлять финтех- и AI-логику в SQL Server.
- Не давать BI прямой доступ к медицинским картам и исследованиям.
- Не делать единый универсальный домен для всех данных.
- Не подключать новых партнёров точечными интеграциями без data contracts.
