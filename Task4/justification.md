# Обоснование Terraform-конфигурации

## Цель инфраструктуры

Инфраструктура поддерживает первый облачный контур для целевой data-платформы «Будущее 2.0»:

- self-service data portal;
- integration layer;
- data platform;
- observability;
- безопасный административный доступ через bastion.

Это не финальная production-платформа, а базовый IaaS-контур, который можно расширять по мере миграции доменов и legacy DWH.

## Выбранные компоненты

| Компонент | Назначение | Почему нужен |
|---|---|---|
| VPC Network | изолированная сеть проекта | отделяет контур data-платформы |
| Public Subnet | публичный доступ к bastion и portal | вход администраторов и пользователей |
| Private Subnet | закрытый контур для внутренних сервисов | защита data platform, integration и monitoring |
| NAT Gateway | исходящий интернет из private subnet | обновления пакетов без публичных IP |
| Route Table | маршрут private subnet через NAT | управляемый egress |
| Security Groups | сетевые правила доступа | минимизация открытых портов |
| Bastion VM | административный вход | SSH не открывается напрямую на private VM |
| Portal VM | self-service data portal | интерфейс для бизнес-пользователей |
| Integration VM | API/Event/ingestion слой | подключение доменов и legacy adapter |
| Data Platform VM | lakehouse/query/data services | обработка и хранение аналитических данных |
| Observability VM | логи, метрики, мониторинг | контроль качества сервисов |
| Additional Disk | диск для data platform | отдельное хранение данных и масштабирование |

## Размеры виртуальных машин

| VM | vCPU | RAM | Boot disk | Обоснование |
|---|---:|---:|---:|---|
| bastion | 2 | 2 GB | 20 GB | достаточно для SSH-доступа и администрирования |
| portal | 2 | 4 GB | 30 GB | MVP self-service портала и лёгкий backend |
| integration | 2 | 4 GB | 30 GB | API/ingestion/event adapter на первом этапе |
| data-platform | 4 | 16 GB | 50 GB + 200 GB data disk | основной узел обработки данных MVP |
| observability | 2 | 4 GB | 50 GB | сбор логов и метрик первого этапа |

Для production-нагрузки data platform должна масштабироваться горизонтально или переноситься на managed/cloud-native сервисы. В рамках IaaS-задания выбран минимальный воспроизводимый стенд.

## Диски

Используются сетевые диски.

Причины:

- диск можно увеличивать независимо от VM;
- data disk отделён от boot disk;
- проще переносить и резервировать данные;
- можно масштабировать хранилище без изменения образа VM.

Для data-platform выделен отдельный диск, потому что именно этот компонент будет работать с витринами, промежуточными наборами данных и ingestion.

## NAT

Private VM не получают публичные IP.

Им нужен исходящий доступ:

- для обновления пакетов;
- для получения контейнеров;
- для подключения к внешним managed-сервисам;
- для интеграций с облачными API.

NAT Gateway решает эту задачу без открытия входящего доступа из интернета.

## Security Groups

Правила разделены по назначению:

- bastion принимает SSH только с `admin_cidrs`;
- portal принимает HTTP/HTTPS из интернета;
- private-сервисы доступны только из private subnet и от bastion;
- исходящий трафик разрешён для установки обновлений и интеграций.

Это снижает риск случайного открытия data platform и observability наружу.

## Что управляется Terraform

Terraform управляет ресурсами, которые должны быть воспроизводимыми:

- сеть;
- подсети;
- маршруты;
- NAT;
- security groups;
- VM;
- диски;
- связи между ресурсами.

## Что разворачивается вручную

Вручную остаются действия, которые зависят от организации и секретов:

- создание cloud account и billing;
- выдача прав сервисному аккаунту;
- production DNS;
- production TLS certificates;
- деплой приложений;
- настройка бизнес-пайплайнов;
- подключение реальных доменных источников.

Эти действия можно автоматизировать позже отдельными модулями или CI/CD pipeline.

## Почему декларативный подход

Terraform описывает желаемое состояние инфраструктуры.

Преимущества:

- инфраструктура воспроизводима;
- изменения проходят через Git и pull request;
- можно увидеть план изменений до применения;
- проще создавать dev/test/prod окружения;
- меньше ручных ошибок;
- легче масштабировать ресурсы;
- проще проводить аудит изменений.

## Как IaC помогает бизнесу

| Бизнес-цель | Вклад IaC |
|---|---|
| Быстрее запускать новые направления | окружения создаются по шаблону |
| Масштабировать аналитику | ресурсы можно увеличивать декларативно |
| Снизить затраты | проще удалять временные стенды и контролировать конфигурации |
| Повысить надёжность | инфраструктура восстанавливается из кода |
| Ускорить time-to-market | команды не ждут ручной настройки серверов |
| Снизить риск ошибок | изменения проходят через plan/review/apply |
