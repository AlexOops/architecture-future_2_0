# Обоснование изменений

## Почему нельзя оставить текущий DWH-центричный подход

DWH на SQL Server 2008 стал узким местом.

Он хранит:

- клиентские данные;
- медицинские карты;
- финансовую историю;
- счета и кредиты;
- данные персонала;
- инвентаризацию;
- финансовую отчётность;
- бизнес-логику.

Такой подход мешает бизнесу:

- отчёты строятся часами;
- новые направления требуют изменений в DWH;
- финтех, AI и медицина зависят друг от друга;
- сложно подключать партнёров;
- PowerBuilder и BI привязаны к legacy-логике;
- медицинские данные смешаны с аналитикой.

## Зачем нужен Lakehouse

Lakehouse нужен для масштабируемой обработки больших объёмов данных.

Бизнес-эффект:

- быстрее строить отчёты;
- хранить сотни ТБ данных дешевле и гибче;
- разделить raw/trusted/curated зоны;
- строить витрины без перегрузки legacy DWH.

## Зачем нужен Self-service Data Portal

Портал нужен, чтобы бизнес-пользователи могли получать отчёты без постоянной зависимости от IT.

Бизнес-эффект:

- быстрее принимать решения;
- сократить очередь запросов к аналитикам и разработчикам;
- дать пользователям поиск наборов данных;
- дать конструктор отчётов в рамках прав доступа.

## Зачем нужен Semantic Layer

Semantic Layer нужен для единых KPI и бизнес-метрик.

Без него разные команды будут считать одни и те же показатели по-разному.

Бизнес-эффект:

- единая версия правды по KPI;
- меньше споров о цифрах;
- быстрее подготовка управленческой отчётности;
- проще масштабировать BI.

## Зачем нужны домены

Домены нужны, чтобы направления могли развиваться независимо.

Бизнес-эффект:

- финтех запускает новые продукты без изменений в медицинском контуре;
- AI развивает модели отдельно от BI и DWH;
- партнёры подключаются по стандартным контрактам;
- медицина сохраняет контроль над medical data.

## Зачем нужны Data Products и Data Contracts

Data Products превращают данные домена в управляемый продукт.

Data Contract фиксирует:

- схему;
- владельца;
- SLA;
- допустимые поля;
- правила доступа;
- версионирование.

Бизнес-эффект:

- проще подключать новые бизнесы;
- меньше ломаются отчёты;
- выше доверие к данным;
- меньше ручных согласований.

## Зачем нужен Data Catalog и Lineage

Data Catalog нужен, чтобы пользователи и команды понимали, какие данные есть и кто за них отвечает.

Lineage нужен, чтобы видеть путь данных от источника до отчёта.

Бизнес-эффект:

- быстрее искать данные;
- проще расследовать ошибки в отчётах;
- выше доверие к аналитике;
- проще проходить аудит.

## Зачем нужен API Gateway и Event Bus

API Gateway нужен для управляемого синхронного взаимодействия.

Event Bus нужен для асинхронных доменных событий.

Бизнес-эффект:

- новые партнёры подключаются быстрее;
- домены меньше зависят друг от друга;
- проще развивать финтех, AI и партнёрские продукты;
- меньше точечных связей через legacy ESB.

## Зачем нужен Terraform

Terraform нужен для воспроизводимого развёртывания облачной инфраструктуры.

Бизнес-эффект:

- быстрее создавать окружения;
- меньше ручных ошибок;
- проще масштабировать ресурсы;
- проще контролировать изменения инфраструктуры;
- ниже затраты на сопровождение.

## Зачем нужен strangler-подход к legacy

Полный отказ от SQL Server 2008 и PowerBuilder за один релиз рискован.

Strangler-подход позволяет:

- оставить legacy как read-only источник;
- переносить отчёты и процессы поэтапно;
- снижать риск остановки бизнеса;
- постепенно выносить бизнес-логику в домены.

Бизнес-эффект:

- миграция проходит безопаснее;
- пользователи не теряют доступ к критичной отчётности;
- можно быстро показать эффект на первых data products.

## Как изменения влияют на бизнес-цели

| Бизнес-цель | Какие изменения помогают |
|---|---|
| Быстрая отчётность | Lakehouse, Marts, Semantic Layer, Portal |
| Независимое развитие финтеха | Fintech Domain, Event Bus, Data Products |
| Независимое развитие AI | AI Domain, Policy Check, Feature Store |
| Подключение партнёров | Partner Domain, API Gateway, Data Contracts |
| Снижение зависимости от DWH | Legacy Adapter, Strangler Migration, Domain Services |
| Качество медицинских сервисов | Clinical Domain, Medical Records Boundary, Access Policies |
| Качество финансовых сервисов | Fintech Domain, отдельные финтех-хранилища, audit |
| Снижение затрат | Cloud scaling, Terraform, FinOps, отказ от legacy-нагрузки |
