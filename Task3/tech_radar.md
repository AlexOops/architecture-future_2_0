# Технологический радар

## Подход

Радар разделён на четыре кольца:

| Кольцо | Значение |
|---|---|
| Adopt | использовать как стандарт для целевой архитектуры |
| Trial | внедрять пилотно в ближайших проектах |
| Assess | изучить и проверить на ограниченных сценариях |
| Hold | не развивать, ограничить или выводить из эксплуатации |

## Adopt

| Технология / подход | Зачем нужен | Бизнес-сценарии |
|---|---|---|
| Cloud Data Platform | масштабируемая работа с сотнями ТБ данных | быстрая отчётность, рост объёмов данных |
| Lakehouse | единая платформа для raw/trusted/curated данных | self-service аналитика, data products |
| Data Products | данные как управляемые продукты доменов | подключение новых бизнесов, независимость доменов |
| Data Contracts | стабильные схемы и SLA между доменами | финтех, партнёры, BI, AI |
| Data Catalog | поиск данных, владельцы, описание наборов | self-service portal |
| Data Lineage | трассировка данных от источника до отчёта | доверие к отчётности, аудит |
| Semantic Layer / Metrics Store | единые KPI и бизнес-метрики | целостная отчётность |
| API Gateway | стандартный вход для API и партнёров | подключение фармы, электроники, финтех-сервисов |
| Event Bus | асинхронные доменные события | независимое развитие доменов |
| IAM / RBAC / ABAC | контроль доступа к данным и отчётам | медицинские и финансовые данные |
| Terraform | воспроизводимая облачная инфраструктура | быстрый запуск окружений |
| CI/CD | управляемый выпуск изменений | снижение time-to-market |
| Observability | метрики, логи, трассировка | качество сервисов и стабильность |

## Trial

| Технология / подход | Зачем нужен | Бизнес-сценарии |
|---|---|---|
| Data Mesh Operating Model | федеративное владение данными | независимое развитие направлений |
| Query Engine поверх Lakehouse | быстрые запросы по большим данным | ускорение отчётов |
| Data Quality Framework | автоматическая проверка качества данных | доверие к отчётам |
| Feature Store | управляемые признаки для AI | развитие ИИ-сервисов |
| Policy-as-Code | проверка политик доступа и инфраструктуры | безопасность medical/fintech данных |
| Strangler Fig Migration | поэтапная замена legacy DWH и PowerBuilder | снижение риска миграции |
| CDC / Streaming Ingestion | near-real-time потоки из доменов | актуальная отчётность |
| Data Product Marketplace | каталог доступных витрин для бизнеса | self-service portal |

## Assess

| Технология / подход | Зачем изучить | Бизнес-сценарии |
|---|---|---|
| Data Virtualization | быстрый доступ к legacy-источникам без полной миграции | переходный период |
| Serverless Analytics | временное масштабирование отчётов | пиковые нагрузки |
| ML Platform / MLOps | промышленный lifecycle AI-моделей | развитие ИИ-направления |
| Privacy Enhancing Technologies | безопасная аналитика чувствительных данных | медицинские сценарии |
| Multi-cloud DR | отказоустойчивость критичных сервисов | надёжность платформы |
| Synthetic Data | тестирование и AI без сырых medical данных | безопасность и разработка |

## Hold

| Технология / подход | Почему ограничить | Что делать |
|---|---|---|
| SQL Server 2008 как центральный DWH | устаревшая платформа, узкое место отчётности | перевести в read-only источник и мигрировать |
| Бизнес-логика в DWH | блокирует развитие доменов | выносить в доменные сервисы |
| PowerBuilder для новых процессов | legacy UI, сильная связка с DWH | не развивать, заменить новыми порталами |
| Точечные интеграции через старую ESB | хрупкие связи, сложное подключение партнёров | заменить API Gateway + Event Bus |
| Прямой BI-доступ к DWH | тяжёлые запросы и разные KPI | перевести BI на Semantic Layer |
| Медицинские карты в аналитической витрине | противоречит бизнес-ограничению и рискам ИБ | исключить из self-service аналитики |
| Ручные выгрузки Excel | плохое качество и неконтролируемые копии | заменить data products и portal |

## Ключевой вывод

В первый год нужно стандартизировать целевые технологии вокруг Lakehouse, Data Products, Data Catalog, Semantic Layer, API Gateway, Event Bus и Terraform.

Legacy DWH, PowerBuilder и точечные интеграции не удаляются одномоментно, но переводятся в режим ограниченного развития и поэтапной миграции.
